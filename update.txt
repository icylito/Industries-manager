3. The migration "failures"
---------------------------
- Not a bug. check_migration was run without the settings the testing README documents for this migration:
    EXPECT_CHANGED=Industries,UserTables KEPT=Industries,UserTables
- The newest data migration, OneNameRule, rewrites rows on purpose:
    - Industries: a later company whose name matches an earlier one (ignoring case, accents and punctuation) is
      flagged with DuplicateOf.
    - UserTables: a later table with a clashing name gets its number added, for example "Sales (12)".
    - Going back keeps those flags and renames on purpose.
- Run as documented it passes: MIGRATION OK, 13 ok. The earlier run on db07138 failed for the same reason.

5. Why backend/ instead of keeping everything in api_v2/
-------------------------------------------------------
- Each layer is now its own project, so the compiler refuses a wrong-way reference. That's the enforcement.
- api_v2.csproj compiles every .cs file under its own folder, so a layer project inside api_v2/ would be compiled
  twice unless fenced off with fragile exclude rules. That's why the layers sit beside it, not inside it.
- The host stayed in api_v2/ on purpose, so start.bat, the launch settings and the ../backups, ../backup-key style
  paths didn't change.
- The name "backend/" was the owner's choice when the layout was asked. A separate folder for the layers is
  standard practice; the name itself (backend/, src/) is taste.
- Keeping it all in one project with folders was the previous state. It works, but nothing stops a layer reaching
  the wrong way except habit.

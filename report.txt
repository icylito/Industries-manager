How it was made, in order:
1. The box has no Docker daemon, so Postgres 16 was started by hand on port 5433 with postgres/postgres (same as docker-compose.yml), the .NET 10 SDK came from the Microsoft apt repo, and the API built main and collector itself on first start. The first admin password was read from the API window like on a real first start.
2. Restore design. pg_restore is its own program with its own connection, so it can't join a transaction. That's why the dump goes into a scratch database first (main_restore_scratch, dropped before and after every run), and the rows are then moved from our own connection with COPY ... TO STDOUT piped into COPY ... FROM STDIN, both binary, inside one transaction on the live database. The table list is Industries, RuleVersions, Requests and Settings, written down once in BackupRestore.cs, so Users and Sessions can't come along by accident. The dump's own __EFMigrationsHistory is compared with today's before the swap, backup.json only drives the button on the page. Sequences are set past the highest restored id afterwards, the rules and settings in memory are read again from the database, and one "restore-backup" line goes to the change log.
3. Big tables. RestoreAsync and ImportAsync in TableWriter.cs used one INSERT ... RETURNING per row, and import read each row back with one more query, so 20,000 rows meant 40,000 round trips. Both write with one binary COPY now. Import takes its ids from the sequence first (nextval over generate_series), so a row that copies an earlier row in the same import can point at it, and reads the saved rows back with one query at the end.
